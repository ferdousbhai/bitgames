# Catalogue wipe and Cloudflare cleanup plan

The owner approved this exact 89-ID wipe with “Yes do it” on 2026-10-08. The local and remote wipe is complete and verified. The owner requested an audit before continuing development, and intends to wipe the poor/duplicative games. The owner confirmed the original games and Splash Tank (separate repository) are favourites; protect them. All 89 approved generated-game folders and their generator are removed locally. Fourteen existing target Workers, fourteen store games and 220 versions were deleted; the other 75 target Workers were already absent. All 41 unrelated Workers and unrelated store records were preserved. See [remote execution evidence](remote-retirement-2026-10-08.json).

## Identify the exact scope

Use the combined per-game judgments and `resource-inventory-2026-10-08.json`. The inventory covers 101 local projects and 101 configured Worker identities; 26 projects have recorded deployment URLs. These counts do not prove current remote existence/listing, nor that the other 75 Workers never existed. Check all selected identities against the actual account inventory, including orphan deployments.

Preserve owner-confirmed favourites. The owner explicitly identified the original games as favourites: protect all 12, plus Splash Tank outside this repository. The source reviews are not a new quality guarantee. Rework means the current product does not meet the bar; an idea may be worth rebuilding as one stronger game, but it should not remain released on that basis. Do not use an agent's source-only judgment as proof that a particular child dislikes a game.

## Execute only the agreed wipe set

1. Record the exact game IDs, configured Worker names, target Cloudflare account, current deployment IDs/bindings and listed store revisions. Retain an auditable before/after record. Do not target by broad `bitgames-*` wildcard or infer a Worker name from a version-prefixed preview hostname.
2. Remove agreed games from the source catalogue/build inputs and example directories, regenerate the browsing catalogue, and remove their workspace/lockfile importers. Update counts and curriculum/shipment tests around the surviving games. Removing public folders alone is insufficient: `examples/_studio/build.mjs` recreates every catalogue entry. Preserve infrastructure still needed by the original games (`package-originals.mjs`, learning helpers, original assets/builders) and shared runtime used by survivors.
3. Prevent store resurrection before reseeding: `apps/store/scripts/db.ts:seed` upserts every example with a URL as `live = 1`. A takedown alone can be reversed by the next seed. Do not run the old bulk seed/release workflow while selected metadata remains eligible.
4. Inspect listed versions/revisions and take selected games down using the repository's review workflow. This removes listings but leaves shared playback and history. A full store wipe additionally needs a scoped, reviewed removal of selected game records/version history, then verification that direct share/version gateways no longer play them. `games-store.ts:deleteGame` is creator-owned; seeded first-party rows are not automatically deletable through a normal creator call. Do not assume takedown, removing local folders or deleting a Worker purges the store database.
5. Delete only the agreed, verified game Workers in the correct account; include their game-specific deployments/preview identities and inspect the outcome. Review any actual resource bindings first. Local example configurations contain no D1/R2/KV/Durable Object/queue/service binding keywords; that is not proof that remote bindings/resources do not exist. Preserve the store Worker, store database, shared multiplayer infrastructure and unrelated games. Delete a separate resource only when exclusive ownership by an agreed removed game is verified.
6. Verify selected workers are absent remotely, selected store entries/share links/version endpoints are retired, and reseeding/building cannot recreate them. Check retained games and favourites still load and play. Record partial failures; do not claim released resources until remote absence is verified. Commit/push the exact source cleanup and evidence when Git writes are available.

Cloudflare documents Worker deletion and a dry-run option in [Wrangler's Worker commands](https://developers.cloudflare.com/workers/wrangler/commands/workers/#delete). Use the installed tool's actual help and account inventory before executing; the repository uses `cf` for deploys and does not contain an established destructive cleanup script. This plan intentionally does not supply a blind bulk-delete command.
